The model

Hallucination is a property, not a bug

  • Predicts the next token. Plausible, not correct.
  • Context is finite — and rots. The start is forgotten first.
  • Split the problem before you prompt.
Say

Under the hood

Your agent doesn't know. It reasons, acts, and observes.

The only thing an agent can trust is what a tool showed it. Every check you give it is one more true observation in the loop.

Say

Slide 6 nói model không có bộ kiểm-sự-thật; vậy sao agent vẫn sửa được bug thật? Vì tool bọc model trong vòng lặp ReAct: reason → act → observe → lặp. Bước observe là điểm duy nhất sự thật bên ngoài đi vào. Chat là một lần, không có observe; agentic là nhiều vòng.

Ba hệ quả SOP: (1) agent chỉ đáng tin bằng thứ tool cho nó thấy — không có test thì observe chỉ có "file đã ghi" và nó báo done; (2) bước reason là chỗ nó tự tin sai, đọc log tool call quan trọng hơn đọc lời giải thích; (3) bước act là chỗ giới hạn quyền — đọc thoải mái, chạy test được, push / rm / cài package phải qua người (slopsquatting, 1.9M rows).

Patterns → practices

Every agent pattern has a failure mode. Every SOP step plugs one.

Planner / Executor

Plan is wrong → every step is wrong

Approve spec.md first · one test per step

Multi-agent

Roles overlap, nobody owns the result

Writer / Reviewer split · one human signs

Memory-augmented

Stale memory repeats the same mistake

Keep CLAUDE.md short and true · /clear when dirty

Tool-using

Wrong write access, wrong package

Least privilege · installs and pushes go through a human

Context · Verification · Ownership — each pattern is one of the three pillars, mechanised.

Say

Bốn pattern mọi agentic coding tool đều dùng, và với mỗi cái: làm gì, hỏng ở đâu, bước SOP nào bịt chỗ hỏng. Planner/Executor = Explore→Plan→Code→Commit (slide 12), duyệt spec trước, task nhỏ một test. Multi-agent = Writer/Reviewer (slide 15) + sub-agent chỉ trả tóm tắt (slide 11), một người ký. Memory = CLAUDE.md / todo.md ngắn và đúng, /clear khi bẩn; "agent nhớ được thì phải chịu trách nhiệm được". Tool-using = quyền tối thiểu; cài package, push, chạm production qua người (slide 16, 25).

Chốt: bốn pattern giải thích vì sao checklist ở slide 21 có đúng những bước đó, và bỏ một bước là mở lại đúng một chỗ hỏng.

06

The dark factory

When no human writes, reviews, or tests the code

No human writes, reviews, or manually tests code. Humans write specs and acceptance criteria; automated systems do the rest.

Say

Mô hình Dark Factory, nhà máy tối: một triết lý thiết kế quy trình phát triển phần mềm mà ở đó không có con người tham gia viết code, review code hay kiểm thử thủ công. Con người chỉ viết đặc tả hệ thống (specs) và tiêu chí nghiệm thu; toàn bộ phần việc còn lại do các hệ thống tự động thực hiện.

Năm mục: vấn đề thực tế, khung cấp độ tự động hoá, bốn giai đoạn triển khai, kiến trúc bốn lớp, rủi ro và giải pháp.

1 · The problem with AI adoption today

Say

Nút thắt cổ chai bị dịch chuyển: nhiều tổ chức ăn mừng quá sớm khi trang bị Cursor, Copilot, Cody giúp gõ code nhanh hơn. Nhưng tốc độ viết code chỉ đẩy nút thắt xuống các khâu sau: lập trình viên vẫn chờ review hàng giờ (thường chỉ mang tính thủ tục hoặc bắt lỗi phong cách) và mất nhiều thời gian kiểm thử thủ công trên localhost.

Khảo sát thời gian thực tế của một đội kỹ sư: phần lớn thời gian lãng phí vào khâu phi sản xuất: chờ review PR 2–8 giờ, trao đổi qua lại 30–90 phút, kiểm thử thủ công 30–60 phút.

2 · Autonomy levels

Five levels, borrowed from self-driving cars

Level 1

Autocomplete

AI finishes your sentences. You do everything else.

Level 2 · you are here

Whole files

AI writes functions or files. You review every change.

Level 3

Spec → code

Holdout scenarios gate quality. You approve the merge.

Level 3.5

Some auto-merge

Same, except some services merge without you.

Level 4

Dark factory

Specs in, tested code out, merged. Your pipeline deploys it.

Most teams: Level 2. The hard design problems live between 2 and 3.

Say

Khung cấp độ tự động hoá, lấy cảm hứng từ xe tự lái. Cấp 1: AI tự hoàn thành câu lệnh, con người làm mọi thứ khác. Cấp 2: AI viết toàn bộ hàm hoặc file, con người review từng thay đổi nhỏ; hầu hết đội ngũ hiện nay dừng ở đây. Cấp 3: AI tạo code từ specs, kịch bản holdout kiểm soát chất lượng, con người phê duyệt merge. Cấp 3.5: như cấp 3 nhưng một số dịch vụ tự merge. Cấp 4, Full Dark Factory: đặc tả đi vào, mã nguồn đã qua kiểm thử tự động được merge ra, CI/CD sẵn có tự deploy.

3 · Phased rollout

Four phases. Each one pays off on its own.

Phase 1

Better context

AGENTS.md · build-before-push · linters that talk to agents

Phase 2

Spec-driven + holdout

Spec in, validated code out. Humans still approve.

Phase 3

Remove the gate

One service at a time, by the numbers.

Phase 4

Full dark factory

Configuration, not architecture.

Nothing downstream of merge changes. It replaces the person typing code and the person squinting at a diff. Your deploy pipeline is untouched.

Say

Lộ trình chia bốn giai đoạn, mỗi giai đoạn tự mang lại giá trị độc lập ngay lập tức mà không cần đợi hoàn thành toàn bộ dự án. Giai đoạn 1: tối ưu ngữ cảnh cho agent. Giai đoạn 2: phát triển hướng đặc tả với kịch bản holdout. Giai đoạn 3: loại bỏ cổng kiểm soát của con người. Giai đoạn 4: Dark Factory toàn phần. Không đụng pipeline deploy sẵn có.

Phase 1 · Context optimization

Give the agent the right context, not more context

# AGENTS.md — QueryEngine (~100 lines)

## What this service does
Query execution layer. Receives SQL,
validates, runs it, returns results.

## Architecture
- Java 21, Spring Boot 3.5, Gradle
- JWT auth on all endpoints

## Key patterns
- Controllers extend generated OpenAPI interfaces
- See docs/coding-patterns.md

## Directory map
- .../controller/  REST endpoints
- .../service/     business logic
AGENTS.md · progressive disclosure

A table of contents, not an encyclopedia. The agent reads the map; needs auth? drills into docs/auth.md. Written Thursday afternoon, obvious by Friday morning.

Build before push

Agent runs build + full test suite locally. Fix it there, not in CI ping-pong.

Linters that talk to agents

Encode architecture rules as lint checks. Write the error as an instruction:

✗ descriptionService layer depends on controller layer.
✓ instructionService imports from controller package. Move the shared type to the model package.
Say

Tài liệu hiển thị thông tin luỹ tiến (progressive disclosure): file AGENTS.md khoảng 100 dòng làm bản đồ tổng quan về cấu trúc dịch vụ, kiến trúc, quy luật code; kết hợp thư mục docs/ chứa tài liệu chi tiết (auth, testing, API) để agent truy xuất khi cần. Tránh quá tải thông tin cho AI.

Quy tắc build-before-push: ép agent tự chạy build và bộ test cục bộ trước khi push.

Linter hướng dẫn hành động: thông báo lỗi viết dưới dạng chỉ dẫn giải quyết thay vì chỉ mô tả lỗi, ví dụ "hãy di chuyển type dùng chung sang gói model".

Phase 2 · Spec-driven development

Specs in Markdown: features describe requirements, bugs describe symptoms

feature spec--- target_repo: ExampleOrg/QueryEngine type: feature --- # Add SQL validation endpoint ## Goal POST /api/v1/sql/validate — validate without executing. ## Requirements - syntax · reject non-SELECT · detect injection - structured JSON result ## Constraints - follow existing controller patterns - full test coverage · no new dependencies
bug spec--- target_repo: ExampleOrg/WritebackService type: bug-fix --- # Writeback returns 500 when supplier is null ## Symptom POST /oracle/writeback with null supplier → HTTP 500 ## Expected HTTP 400 with a validation error mentioning "supplier" ## Do not assume the root cause. Investigate the codebase.

A bug spec describes the symptom and nothing else. Not "the null check is missing on line 47." The agent goes and finds out why.

Say

Đặc tả dạng Markdown. Lập trình viên viết feature spec (mô tả yêu cầu, ràng buộc) hoặc bug spec (chỉ mô tả triệu chứng, để agent tự tìm nguyên nhân gốc rễ).

Bug spec không nói "tôi nghĩ thiếu null check ở dòng 47"; nó nói endpoint trả 500 khi supplier null, phải trả 400 với lỗi validation. Agent tự điều tra codebase.

Phase 2 · Holdout scenarios, the core of the system

The coding agent never sees the acceptance tests.

# SQL Injection Detection · P0
POST /api/v1/sql/validate with
  sql: "SELECT * FROM users; DROP TABLE users; --"
Then valid should be false.
Errors should mention disallowed statement types.

Spec is the training set. Scenarios are the test set. The wall between them is what makes the gate mean anything.

3 runs, 2 of 3 must pass · 90% of scenarios gate the PR · a failing agent gets one line back, never the scenario text. No glue code: the evaluator adapts, so scenarios don't rot like Cucumber step definitions.

Say

Kịch bản holdout là cốt lõi của hệ thống: các bài kiểm thử chấp nhận viết bằng tiếng Anh tự nhiên theo định dạng BDD, lưu trong thư mục cách ly mà agent viết code không thể truy cập.

Một bộ đánh giá độc lập dùng LLM lập kế hoạch các cuộc gọi API kiểm thử trên một môi trường triển khai tạm thời (ephemeral deployment) và đánh giá phản hồi.

Kịch bản chạy 3 lần, đạt tối thiểu 2/3 để tính pass nhằm khử tính bất định của LLM; tổng tỷ lệ pass phải trên 90% để vượt cổng chất lượng.

Giải quyết triệt để vấn đề mục nát glue code của các công cụ BDD truyền thống như Cucumber: không có step definition, bộ đánh giá tự thích ứng khi API đổi.

Phase 2 · The human role → Phase 3 · Removing the human gate

Review the report, not the code. Then let the numbers open the gate.

Phase 2 · review results, not code

"Did the scenarios pass? What's the satisfaction rate?" Glance at the diff, click merge.

Five minutes, not two hours.

Maintenance agents

Weekly sweeps for drift, stale docs, outdated patterns. Small cleanup PRs through the same gate. Garbage collection for the codebase.

Phase 3, one service at a time: swap label for review → merge, only when the last 20 PRs show:

MetricThreshold
Scenario pass rate> 90%
False positives — scenarios said yes, code was broken< 5%
Human override — human rejected what scenarios passed< 10%

Any team member can still block before the merge window closes. Earn the trust. Don't declare it.

Say

Vai trò con người ở giai đoạn 2: không đọc code từng dòng nữa mà xem xét báo cáo kết quả của các kịch bản kiểm thử, mất khoảng 5 phút thay vì 2 giờ.

Giai đoạn 3: áp dụng auto-merge cho một số dịch vụ đạt chỉ số an toàn: tỷ lệ pass kịch bản trên 90% trong 20 PR gần nhất, tỷ lệ báo lỗi giả dưới 5%, tỷ lệ con người ghi đè hoặc từ chối dưới 10%.

4 · Four-layer architecture

Four layers. The boundaries matter more than the guts.

Inputshumansspecs · holdout scenarios · AGENTS.md · linter rules
Code generationautonomousreads spec + repo knowledge → generates, builds, tests, self-reviews, opens PR
the wall · agent can't see scenarios · evaluator doesn't care how code was made
Validationautonomous · isolatedstandard CI first, then scenario evaluator on an ephemeral deployment
Merge & deployautonomous + your infraauto-merge to main, then the pipeline you already have

Code generation and validation must be completely isolated, or the agent can game the test or learn the exam by heart. Same principle as train/test separation in ML.

Say

Kiến trúc bốn lớp. Inputs, con người sở hữu: specs, kịch bản holdout, AGENTS.md, luật linter. Code Generation, tự động: agent đọc spec và ngữ cảnh repo, tự sinh mã, build, test tại chỗ, tự review và mở PR. Validation, tự động và cách ly: chạy CI truyền thống, rồi bộ đánh giá kịch bản chạy thử trên môi trường tạm thời. Merge và Deploy, tự động cộng infra sẵn có: tự merge vào nhánh chính và kích hoạt pipeline CI/CD hiện có.

Lưu ý cực kỳ quan trọng: lớp Code Generation và lớp Validation phải cách ly hoàn toàn để tránh agent gian lận hoặc học vẹt bộ đề thi.

5 · Risks and mitigations

Four things that go wrong, and what catches each

The evaluator approves broken code3 runs per scenario · 90% pass gate · manual audit of the first 50 PRs · the traditional CI/CD suite still runs after merge
Engineers resist: identity is tied to writing codeShift the role up: defining the product and controlling quality is higher-level product engineering, not less engineering
API costs climb with retriesHard cap of 3 attempts per spec · token monitoring with alerts
Scenarios go stale as APIs changeLLM evaluation adapts to API shape without glue code · weekly upkeep by maintenance agents
Still true at every level

An agent with the wrong write access wiped 1.9 million production rows. You still own the incident.

Say

Bộ đánh giá duyệt nhầm code lỗi: giảm thiểu bằng chạy kịch bản 3 lần, cổng pass 90%, kiểm toán thủ công 50 PR đầu tiên, và giữ nguyên bộ CI/CD truyền thống chạy sau merge.

Kháng cự từ đội ngũ kỹ sư: kỹ sư gắn bản sắc cá nhân với việc trực tiếp viết code. Giải pháp là chuyển dịch vai trò sang định nghĩa sản phẩm và kiểm soát chất lượng, kỹ thuật sản phẩm cao cấp hơn.

Chi phí API tăng cao: giới hạn cứng tối đa 3 lần thử lại cho mỗi spec, giám sát token kèm cảnh báo.

Kịch bản kiểm thử lỗi thời: đánh giá bằng LLM tự thích ứng với thay đổi cấu trúc API mà không cần bảo trì glue code, kết hợp bảo trì hằng tuần bởi agent chuyên trách.

Giữ sự cố 1,9 triệu dòng để nhắc: dù tự động đến đâu, người cấp quyền vẫn sở hữu sự cố.

Slide 25 để lại câu hỏi: agent tự chạy không ai xem, làm sao biết nó đã làm gì. Ba lớp: logging (hệ thống ghi từng tool call, không phải "báo cáo" model tự viết); tracing (nối log thành đường thực thi, lần ngược từ hành động về suy luận, thấy chỗ tốn thời gian và token); audit trail (append-only, kiểm soát truy cập, trả lời quyết định gì, đọc dữ liệu gì, ai duyệt). Log để debug, audit để chịu trách nhiệm.

Ba nhóm metric: vận hành, tin cậy (tỷ lệ escalate nói thẳng agent đang ở nấc nào), governance. Stack là cùng stack team đã dùng cho service; agent chỉ là một service nữa. Observability phải là lớp thiết kế từ đầu, không phải monitoring gắn sau sự cố.
