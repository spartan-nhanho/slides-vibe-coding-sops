The claim we are not making

Code 10x faster with AI.

You will type less. That is not the same as shipping more. The bottleneck was never typing — it was understanding, reviewing, and being right.

Speaker notes

This is deliberate. The old version of this lecture led with "10x faster" and the rest of it argues against that. Name the tension early.

What actually changes

Cheaper now
  • First drafts
  • Boilerplate — DTOs, mappers, scaffolding
  • Explaining unfamiliar code
  • Test skeletons
  • One-off scripts and migrations
Exactly as expensive
  • Knowing what to build
  • Reviewing the diff
  • Owning the incident
  • Deciding the tradeoff
  • Being right about the edge case

Part one

Key concepts

Seven words you need to use precisely for the rest of the course.

Concept 1

Context engineering

The model is only as good as what you put in front of it: the repo's conventions, the failing test, the actual stack trace.

Prompt wording matters far less than context. Rewriting "please carefully" into "you are an expert" changes nothing. Pasting the error changes everything.

Speaker notes

Counter the prompt-magic-words folklore here. Ask: when the model got it wrong last week, was the prompt bad, or did it not have the file?

Concept 2

Project context files

Encode conventions once, so every session starts informed instead of guessing.

# CLAUDE.md / AGENTS.md / .cursor/rules

## Build
Prefer `make` over raw gradle — it sets profiles the raw command doesn't.

## Migrations
Forward-only. Never edit an applied migration.

## Authorship
No AI co-author trailers on commits. Ever.

If you correct the model on the same thing twice, it belongs in this file.

Concept 3

Agentic vs. chat

Chat
  • You carry the context in and the code out
  • Good for: explaining, designing, one function
  • Fails by: inventing APIs it can't check
Agentic
  • It reads files, edits, runs tests, iterates
  • Good for: multi-file changes, refactors, test loops
  • Fails by: confidently green tests that assert nothing

Different tools, different failure modes. Review accordingly.

Concept 4

Hallucination check

Verify every external API, config key, and library method against the real source. Model memory is not a source.

  • The package that doesn't exist
  • The method that was removed two majors ago
  • The config key that is almost right
  • The citation to documentation that was never written
Speaker notes

The "almost right config key" is the dangerous one — it fails silently at runtime in staging, not at compile time.

Concept 5

The safe zone

Highest value, lowest risk: code that is tedious, mechanical, and immediately verifiable.

Let it drive
  • DTOs and mappers
  • Test scaffolding
  • Migration skeletons
  • Repetitive refactors
  • Docs from existing code
You drive
  • Auth and permissions
  • Money arithmetic
  • Concurrency
  • Anything destructive
  • The bit you don't understand yet

Concept 6

You are the author

AI authorship is invisible to reviewers and to production.

Nobody debugging this at 2am cares which tool typed it. The commit has your name on it because the responsibility does.

No Co-authored-by trailers. No "generated with". Strip them before you push.

Concept 7

Rubber ducking 2.0

Using the model to explain a bug you understand badly — and noticing that the act of writing the question is what solved it half the time.

Write down your own hypothesis before you ask. Otherwise the first plausible answer becomes your hypothesis, and you have outsourced the thinking you were supposed to do.

9.1

AI-assisted development workflow

Giving context

Include
  • The failing test
  • The actual error, in full
  • The file being changed
  • The conventions file
  • One neighbouring example of the pattern
Leave out
  • The whole repo
  • Six abandoned attempts
  • Unrelated files "for context"
  • Secrets, dumps, customer data

More context is not better context. Noise dilutes the signal you actually need it to weigh.

Iterative refinement

Small diffs, tests between steps

A 600-line change you cannot review is worse than no change. Break the work so that every step ends at a state you can run.

  1. Describe the change and the constraint
  2. Take one step
  3. Run the tests
  4. Read the diff
  5. Correct the model, or correct yourself

The skill nobody teaches

Knowing when to stop

Three failed attempts on the same problem is a signal, not an invitation to prompt harder.

  • The model is looping over the same wrong idea
  • You are pasting errors without reading them
  • The diff is growing and the test is still red
  • You could not explain the current state of the code

Close the tab. Write it yourself. It will take twenty minutes.

Speaker notes

Ask the room for the longest they've ever spent fighting a model on something they could have written by hand. There's always a good war story here.

9.2

Code review process

The shift

Review used to catch what you forgot. Now it catches what you never knew was there.

Code you wrote has a shape in your head. Code you accepted does not. The review has to build that shape from scratch — which is slower, not faster.

Security

What gets dropped silently

  • Authorization checks — the refactor kept the happy path and lost the guard
  • Injection — string-built SQL because the prompt said "dynamic filter"
  • Secrets in code — a plausible-looking default that is a real key shape
  • Unsafe deserialization — accepting a type it shouldn't
  • Error bodies that leak — stack traces returned to the client
Speaker notes

The dropped authz check is the single most common real-world AI review miss. It never shows up in tests because the tests were generated from the same happy path.

Performance

The four smells

  • N+1 queries — the loop that looks innocent
  • Missing index — the new WHERE column nobody indexed
  • Unbounded fetch — findAll() against a table that grew
  • Accidental O(n²) — a nested includes() over two lists

All four pass every unit test. All four are fine on ten rows.

Testing generated code

Tests that assert the implementation

// Generated test. Green. Worthless.
test('applies discount', () => {
  const spy = mock(pricing.discountFor)
  pricing.total(cart)
  expect(spy).toHaveBeenCalled()          // ← asserts a call
})
// Asserts the behaviour anyone actually cares about.
test('10% off at exactly 100 units', () => {
  expect(pricing.total(cartOf(100))).toBe(900_00)
})

If the test would still pass after you delete the business rule, it is not a test.

9.3

Documentation

Direction matters

Docs from code, not code from docs

Generating documentation from real code works, because the source of truth is checked in and the model is summarising something it can see.

Generating code from a prose description of what you wish existed produces something that looks like it matches — and drifts the moment either side changes.

API documentation

Spec first, generate outward

  • The OpenAPI spec is the contract, not a description of the contract
  • Server stubs and typed clients are generated from it
  • Never hand-edit generated sources — change the spec, regenerate
  • Generation runs in CI, so drift fails the build instead of surprising the frontend
Speaker notes

Tie to whatever the students' own repo does — the generated api/generated-* directories exist precisely so this rule can be enforced.

ADRs

Architecture decision records

Belongs in one
  • The decision, in one sentence
  • What was true when you made it
  • The options you rejected and why
  • What would make you revisit it
Does not
  • How the code works today
  • Anything the code already says
  • A tutorial for the library you picked
  • Four paragraphs of AI-generated preamble

An ADR is a decision with its expiry conditions. If it has none, it's a wiki page.

9.4

The SOPs

Five checklists. The point of a checklist is that you run it when you are tired, in a hurry, and confident. That is exactly when you skip it.

SOP-1

Verifying AI-generated code before you commit

  1. Read every changed line. If you can't explain a line, it doesn't go in.
  2. Verify every external API, config key, and library method against real docs.
  3. Check imports: no invented packages, no version the lockfile doesn't have.
  4. Run the build and the full suite locally, not just the new test.
  5. Diff-read for dropped behaviour: auth, nulls, error branches, logging.
  6. Check for hardcoded values, credentials, leftover placeholders.
  7. Strip AI authorship trailers. You are the author.
  8. Re-read the diff as if a stranger wrote it. Because one did.
SOP-2

Setting up a new service

  1. Scaffold from the canonical templates. Never copy a live service to seed a new one.
  2. Confirm which environment-selection model the infra uses before touching Terraform.
  3. Put values where they belong: shared config vs. per-env vars vs. secrets.
  4. Wire CI/CD and observability before the first real endpoint.
  5. Open a draft PR early so the pipeline runs against a real branch.
Speaker notes

Step 1 exists because copying a live service carries its incidents, its dead flags, and its hardcoded account IDs into the new one.

SOP-3

Database migrations

  1. Forward-only and immutable once merged. Never edit an applied migration.
  2. Expand → migrate → contract. Never drop a column in the release that stops writing it.
  3. Review the generated SQL by hand: types, nullability, defaults, index coverage.
  4. Estimate lock impact on the production row count, not your local ten rows.
  5. Run it against a realistic dataset before it reaches staging.
  6. Write the rollback plan down before you apply.
SOP-4

API endpoint creation

  1. Contract first — define the schema, then generate.
  2. Never hand-edit generated sources; change the spec and regenerate.
  3. Validate input at the boundary. Authorize on every endpoint, not just the obvious ones.
  4. Decide the error contract explicitly: status codes, body shape, what leaks.
  5. Pagination and limits from the start. An unbounded list endpoint is a future outage.
  6. Test: happy path, auth failure, validation failure, empty result.
SOP-5

Integration testing

  1. Real dependencies in containers over mocks wherever practical.
  2. Each test owns its data and cleans up. No ordering dependencies.
  3. Tag integration tests separately so unit runs stay fast in CI.
  4. Assert on observable behaviour, not internal calls.
  5. A flaky test is a failing test — fix it or delete it, never retry it away.

45 minutes

The Legacy Rescue

One function. Undocumented, badly named, and wrong in ways the tests don't currently catch.

Setup

Two commands, no install

git clone https://github.com/spartan-nhanho/slides-vibe-coding-sops
cd slides-vibe-coding-sops/legacy-rescue && node --test

You get src/billing.js — a quote calculator carried over from a service nobody maintains — and a test file that passes. The passing tests are part of the problem.

Node 20+ No dependencies No build step

The tasks

  1. 10 min — Use AI to explain what the code does. Write your own hypothesis about the bug first.
  2. 15 min — Refactor toward clean code with AI assistance. Small steps, tests between steps.
  3. 10 min — Generate unit tests for the refactored code.
  4. 10 min — Manual: run them, then find at least two edge cases the AI missed and add them yourself.

There are four seeded bugs. Most people find two.

Speaker notes

Don't say how many bugs there are until the debrief if you want the honest version of the exercise. The slide says four — hide it or change it depending on how you want to run the room.

Rules

  • You may use any model or tool you like
  • You may not paste a fix you cannot explain
  • Every commit is authored by you
  • Keep a note of every time the model was confidently wrong — that's the debrief material

Debrief

Three questions

  1. Which part did the AI genuinely do better than you would have?
  2. Where did it mislead you confidently?
  3. Which SOP step would have caught the bug you missed?

Part three

Checkpoint questions

Easy

What is the danger of copy-pasting code straight from an LLM into production?

Looking for

Not "it might be wrong" — that's true of all code. The specific danger: it is plausible, so it survives the skim that catches obviously-wrong code, and nobody has the mental model needed to debug it later.

Easy

Why should AI co-author trailers never appear on a commit?

Looking for

Accountability. Blame, review, and incident response all assume a human owner. A trailer diffuses that, and it tells reviewers to lower their standard for the diff — the opposite of what it should do.

Medium

How do you structure a prompt to get a SQL query optimized specifically for Postgres?

Looking for

Give it the DDL, the existing indexes, the row counts, the Postgres version, and the current EXPLAIN ANALYZE. Ask for the plan it expects. Then run the real EXPLAIN — the answer is verified against the planner, not against the model.

Medium

You ask AI to add a column to a table with 40M rows. What must you check before applying?

Looking for

Whether the default forces a table rewrite, what lock level is taken and for how long, whether the migration runs inside a transaction that will hold that lock, index creation being CONCURRENTLY, statement timeouts, and the rollback. SOP-3, steps 3–6.

Hard

AI generated a regex for email validation. It looks correct. What is your SOP to verify it is safe against ReDoS?

Looking for

Read it for nested quantifiers and overlapping alternation — the catastrophic-backtracking shapes. Test with adversarial input, not valid input: a long run of the ambiguous prefix plus one character that fails. Measure the time; it should not grow superlinearly. Then question the premise — validating email by regex is the wrong tool. Check for @, bound the length, and send a confirmation mail.

Hard

An AI-assisted PR passes all tests and review, then causes an incident. Where did the SOP fail?

Looking for

Usually not in review — in the tests, which were generated from the same misunderstanding as the code, so they encode the bug as the expected behaviour. Both sides of the check came from one source. The fix is a human-written test derived from the requirement, not from the implementation.

Take three things

  1. Context beats prompting. Give it the error, the test, and the conventions.
  2. Generated tests are not verification. They came from the same misunderstanding as the code.
  3. You are the author. Of the diff, of the incident, of the fix.
